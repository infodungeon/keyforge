**Version:** 2.2 (Complete)
**Date:** 2025-12-29
**Context:** Operational protocols for engineering high-reliability distributed systems with Large Language Models.

## 1. Core Philosophy: Constraint-Based Engineering

LLMs are probabilistic engines, not rational agents. They suffer from **Semantic Blindness** (confusing syntax with logic), **Context Saturation** (degrading reasoning as sessions grow), and **Happy Path Bias**.

To build world-class software, we move from **Asking** (hoping the LLM is smart) to **Constraining** (making it impossible for the LLM to be wrong).

> *"You cannot test quality into a product. Correctness must be a property of the system."*

### The Criticality Tiers

1. **Tier 1 (The Nucleus):** `keyforge-physics`, `keyforge-evolution`.
   * *Role:* Pure Logic. Deterministic. Zero IO.
   * *Risk:* Mathematical hallucination, silent optimization failure.
   * *Requirement:* **95%+ Branch Coverage** + Property Testing (`proptest`) + Shadow Execution.

2. **Tier 2 (The Contract):** `keyforge-protocol`, `keyforge-model`.
   * *Role:* Data Definitions. Validators.
   * *Risk:* Data corruption, serialization bombs.
   * *Requirement:* **100% Validation Coverage**. Use `TryFrom` to make invalid states unrepresentable.

3. **Tier 3 (The Shell):** `keyforge-infra`, `keyforge-hive`, `keyforge-agent`.
   * *Role:* IO, Network, Database, State.
   * *Risk:* Deadlocks, "Whac-A-Mole" debugging.
   * *Requirement:* **Error-First Design**. Define failure modes (`thiserror`) before logic.

## 2. Structural Patterns (The Architecture)

We enforce a strict separation of concerns to isolate LLM hallucinations.

### A. Functional Core, Imperative Shell

We isolate pure logic from the messy real world.

* **The Core (`physics`, `evolution`):** Pure functions only. Input -> Output. No `std::fs`, no `tokio`, no `sqlx`.
  * *Why:* If the Core fails, it is a logic bug (reproducible).
* **The Shell (`infra`, `hive`):** Handles Files, Network, Time, and Database.
  * *Why:* If the Shell fails, it is an environment issue.
* **Constraint:** The Core **NEVER** imports the Shell.

### B. The Semantic Firewall (Aggressive Newtyping)

LLMs struggle to track variable meaning across long contexts. We use the compiler to enforce semantics.

* **Rule:** Never use primitives (`usize`, `f32`) for domain logic signatures.
* **Pattern:**

    ```rust
    pub struct KeyIndex(usize);
    pub struct CharCode(u16);
    // Compiler Error: KeyIndex + CharCode
    ```

* **Effect:** If Gemini hallucinates and swaps arguments, the code fails to compile immediately.

### C. Context Compression (The Header Strategy)

Pasting 50k lines of code guarantees hallucination.

* **Strategy:** Feed Gemini **"Rust Headers"** for dependencies.
* **Action:** When working on `physics`, provide only the `struct` and `fn` signatures of `model` and `protocol`. Strip bodies.
* **Benefit:** Reduces token load by ~90%, keeping the attention mechanism focused on the active task.

## 3. Verification Strategy (The Safety Net)

### A. Coverage-Driven Verification (CDV)

We use coverage tools (`tarpaulin`) to identify **Logic Dark Matter**—code branches generated by the LLM that have never been executed.

* **Rule:** High coverage is not a vanity metric; it is a map of "Unknown Territory."
* **Action:** If a branch is uncovered, the LLM must write a specific test case to hit it, or the code must be deleted.

### B. Shadow Execution (The Oracle)

We maintain a "Simple, Slow, Correct" reference implementation alongside the "Fast, Complex" optimized version.

* **Artifact:** `DeterministicScorer` (in `verification.rs`).
* **Protocol:** Every optimization run in `debug` mode compares `ScoringEngine` (Fast) vs `DeterministicScorer` (Slow).
* **Invariant:** `abs(Fast - Slow) < EPSILON`. If this fails, the system panics.

### C. The "Ghost Code" Strategy

Complex logic overwhelms the LLM's working memory. We provide simplified models for reasoning.

* **Artifact:** `src/ghost.rs` (in Tier 1 crates).
* **Usage:** A simplified, pure-Rust model of the complex kernel.
* **Protocol:** Force Gemini to implement logic against the *Ghost* model first. Once the algorithm is proven, translate it to the optimized kernel.

## 4. The Interaction Protocol (The Process)

We use **Least-to-Most (LtM)** prompting to force "System 2" reasoning.

### Phase 1: The Contract (No Code)

**Prompt:**
> "We are implementing `[Feature]`.
>
> 1. **Define Types:** Create Newtypes for inputs/outputs.
> 2. **Define Invariants:** What must never happen? (e.g., 'Index out of bounds').
> 3. **Draft Tests:** Write a `proptest` that breaks a naive implementation.
> **STOP. Do not write the function body.**"

### Phase 2: The Plan (Pseudo-Code)

**Prompt:**
> "Write the logic in **Pseudo-Rust**. Focus on data flow and borrow lifetimes. Mark `unsafe` blocks explicitly."

### Phase 3: The Implementation (Translation)

**Prompt:**
> "Translate the Pseudo-Rust into real Rust using the Types from Phase 1. Ensure it passes the Draft Tests."

## 5. The Debugging Protocol (Stopping the Spiral)

When the compiler screams, Gemini panics and starts "driving the compiler" (random patching).

### A. The "Reasoning Injection" Loop

**Never** just paste an error.

**Prompt:**
> "The compiler error is: `[Paste ONE error]`.
>
> 1. **Analyze:** Explain *why* this conflicts with the Rust memory model.
> 2. **Hypothesize:** Is this a logic error or a signature mismatch?
> 3. **Plan:** Propose a fix *without* changing public signatures."

### B. The "3-Turn Hard Stop"

If Gemini fails to fix a bug after **two attempts**:

1. **STOP.** Do not paste the third error.
2. **REVERT.** Undo the last AI change.
3. **RESET.** Trigger the "Soft Reset" (below).

### C. The "Soft Reset"

To clear "bad reasoning" from the context window without reloading files:

**Prompt:**
> "🛑 **STOP. IGNORE ALL PREVIOUS ATTEMPTS AT FIXING THIS FUNCTION.**
> We are resetting the approach for `[Function Name]`.
>
> **Current Truth:**
>
> 1. The clean file content is: `[Paste CLEAN code]`
> 2. The specific error is: `[Paste ONE error]`
>
> **Instruction:** Analyze the error against the clean code. Explain the fix in one sentence, then generate the code."
