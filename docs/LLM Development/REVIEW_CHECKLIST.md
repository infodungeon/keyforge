# KeyForge Code Review Checklist

**Context:** Mandatory checks before merging LLM-generated code.

## 1. The Comprehension Test (Human Layer)
- [ ] **Explainability:** Can I explain this logic to a junior engineer *without* reading the PR description?
- [ ] **No Magic:** Are macros, complex generics, or `unsafe` blocks used? (Reject if yes, unless justified).
- [ ] **Naming:** Do variable names reflect *Domain Concepts* (e.g., `finger_load`) or *Implementation Details* (e.g., `f32_val`)?

## 2. The Reliability Test (Machine Layer)
- [ ] **Coverage:** Did `cargo tarpaulin` confirm 95%+ coverage on new logic?
- [ ] **Mutation:** Did `cargo mutants` pass (no surviving mutants)?
- [ ] **Shadow Execution:** Is the `DeterministicScorer` updated to match any changes in `ScoringEngine`?

## 3. The Hallucination Check (AI Layer)
- [ ] **Argument Swapping:** Check all function calls with multiple arguments of the same type (`usize`, `f32`).
- [ ] **Temporal Coupling:** Does the code assume a state (e.g., "Job is running") without checking it?
- [ ] **Happy Path Bias:** Are error cases (Disk full, Network down, Invalid UTF-8) handled explicitly?

## 4. The Database Safety Check
- [ ] **Zero-Touch:** Was the migration generated by a tool/human, NOT the LLM?
- [ ] **Additive Only:** Does the migration only *add* columns/tables? (No `DROP`).

## 5. The "Soft Reset" Trigger
- [ ] If the PR required > 3 attempts to fix a bug, **REJECT**. Request a "Soft Reset" and fresh implementation.
