# ADR-021: Unified Persistence & Protocol for Community Entities

## Status
Accepted

## Context
The project required the addition of complex community and research entities: `UserProfile`, `BiometricProfile`, `LayoutSubmission`, and `AnalysisSession`. Previously, these were handled partially via ad-hoc filesystem storage or were not persisted at all. To support the "Data-Driven Analysis" goal, we needed a unified, relational approach to persistence.

## Decision
1. **Relational Foundation**: Use PostgreSQL via SQLx as the primary persistence engine for community data.
2. **Unified Repository Trait**: Implement a `UserRepository` trait to abstract different persistence backends (Postgres vs Local Fs).
3. **Sparse Biometric Storage**: Store biometric bigram latencies in a relational table (`biometric_latencies`) rather than a blob to enable cross-user research queries.
4. **Integration Layer**: Wire all repositories into the Hive `AppState` to provide a single orchestration point.

## Consequences
- **Pros**:
    - Centralized management of user and biometric data.
    - Enables research-grade analysis of layout performance across users.
    - Improved data integrity via relational constraints and migrations.
- **Cons**:
    - Increased infrastructure complexity (Postgres dependency).
    - Higher overhead for local-only testing (mitigated by `testcontainers`).
