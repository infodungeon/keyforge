# ADR-023: Content-Addressable Job Identification

## Status
Proposed

## Context
The KeyForge system relies on a high-performance `CompiledEngineCache` to avoid re-compiling physics kernels for identical optimization jobs. Currently, a `JobIdentifier` is derived solely from asset metadata (IDs) and scoring weights. If the actual content of a corpus or lexicon is updated in the data store without a change to its ID, the system continues to serve a stale cached engine built from the previous content. This violates the **DATA-005** law regarding cache consistency and data integrity.

## Decision
1. **Cryptographic Fingerprinting**: Transition from "Metadata-Based" to "Content-Addressable" identification.
2. **SHA-256 Integration**: Use SHA-256 to generate a 32-byte content hash for every asset (`Corpus`, `Lexicon`, `Weights`) upon loading into the system.
3. **Immutability of Identity**: The `JobIdentifier` will now incorporate these content hashes. Any change to the input data will automatically result in a unique Job ID, triggering a cache miss and subsequent re-compilation.
4. **Lazy Hashing**: To minimize performance impact, hashes will be computed once during the `load` phase in the `keyforge-infra` layer and stored within the `Asset` domain struct.

## Consequences
- **Pros**:
    - **Guaranteed Consistency**: Eliminates stale state bugs in the optimization pipeline.
    - **Verifiable Results**: Enables exact mapping between an optimization report and the specific version of the input data used.
    - **Transparent Invalidation**: Removes the need for manual cache clearing tools.
- **Cons**:
    - **Computation Overhead**: SHA-256 adds a minor latency hit during asset loading (offset by the infrequency of loads relative to scoring).
    - **Storage Requirements**: Job IDs and Result keys in the database may require expansion to accommodate hashed strings.
