# ADR-024: Typed UI-WASM Boundaries and Determinism

## Status
Proposed

## Context
The KeyForge UI (`keyforge-ui`) interacts with the physics engine via a WebWorker running a WASM module. Current implementation relies on `any` types for the module interface and utilizes non-deterministic `Math.random()` for progress reporting and word scoring. This violates **ARCH-006** (Structural Oracle) and **ARCH-003** (Deterministic Physics), making the UI a "vibe-based" view rather than a faithful representation of the engine state.

## Decision
1. **Strongly Typed Interop**: Implement explicit TypeScript interfaces for all WASM-exported structs and methods. Prohibit the use of `any` in the worker and API layers.
2. **Real-Time State Extraction**: Implement a `get_training_update` method in the WASM kernel to expose actual engine metrics (Score, IPS, Epoch) to the UI.
3. **Seeded UI Determinism**: Replace `Math.random()` with deterministic logic. If UI-side randomness is required for non-critical animations, use a seeded PRNG consistent with the system state.
4. **Automated Sync**: Explore tool-aided type generation (e.g., `wasm-bindgen` or `ts-rs`) to ensure Rust domain models and TS interfaces remain synchronized.

## Consequences
- **Pros**:
    - **Compile-Time Safety**: Catches contract mismatches across the WASM boundary during the build phase.
    - **Bi-Directional Truth**: The UI becomes a pure projection of the deterministic Rust kernel.
    - **Improved DX**: Full autocompletion and type checking for WASM-returned data.
- **Cons**:
    - **Boilerplate**: Requires manual or automated definition of TS interfaces for Rust structs.
